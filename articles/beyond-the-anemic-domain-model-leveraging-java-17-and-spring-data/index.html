Beyond the Anemic Domain Model: Leveraging Java 17 and Spring Data for Bulletproof Business Logic

Most enterprise Java applications suffer from a quiet architectural code smell: The Anemic Domain Model. Here is how to design domain models where illegal states are impossible to represent at compile-time using modern Java 17 records, sealed hierarchies, and Spring Data JPA.

AS
Amit Kumar Shukla Senior Digital Architect

Most enterprise Java applications suffer from a quiet architectural code smell: The Anemic Domain Model. First diagnosed and famously critiqued by Martin Fowler in his seminal 2003 paper (AnemicDomainModel), this anti-pattern describes software systems where domain entities are reduced to passive data bags while business behavior is extracted into procedural service classes.

We’ve all seen it. Entities are designed as passive data holders filled with private fields, boilerplate getters, open setters, and framework-mandated no-arg constructors. The actual business logic is then stripped out and dumped into sprawling, procedural @Service classes. The result? Mutable state floats everywhere, encapsulation is compromised, and invalid combinations (such as an order that is simultaneously Shipped and Cancelled) are caught only at runtime—or worse, quietly persisted to the relational database.

This directly contradicts the core tenet popularized in type-driven domain modeling: "Make illegal states unrepresentable." What if we could design enterprise domain models where the Java compiler itself guarantees business validity before code ever reaches runtime?

In this post, we’ll explore how to harness modern Java 17 language capabilities—specifically Records (JEP 395) and Sealed Classes/Interfaces (JEP 409)—alongside Spring Data JPA and Hibernate 6 to write concise, type-safe, and immutable domain models that enforce their own invariants.

1. The Cost of Mutability in Traditional Domain Design

In a classic JPA setup, entities require default constructors and mutable fields to let Hibernate hydrate objects via reflection. While functional for basic CRUD, this opens the door to developer error: 

// Traditional mutable approach
Order order = orderRepository.findById(id);
order.setStatus(OrderStatus.SHIPPED); 
// Oops! We updated the status without checking if it was previously paid or cancelled.

When business rules are scattered across services, maintaining invariants becomes a game of defensive programming (if/else checks everywhere).

By shifting toward immutability and type-driven design, we can force the compiler to enforce our state machine rules.

2. Modeling Immutable Value Objects with Java 17 Records

In Domain-Driven Design (Eric Evans, 2003), Value Objects (like Money, Address, or EmailAddress) represent descriptive aspects of the domain with no conceptual identity. Because they are defined entirely by their attributes, they must be immutable and self-validating.

Historically, implementing Value Objects in Java required voluminous boilerplate (equals, hashCode, toString, defensive copies) or third-party libraries. With OpenJDK JEP 395 (Records), Java provides first-class support for immutable nominal tuples. Furthermore, Hibernate 6.x+ and Spring Data JPA natively support Java records as @Embeddable types, letting us write rock-solid value objects right out of the box: 

@Embeddable
public record Money(
    @Column(name = "amount", nullable = false)
    BigDecimal amount,
    
    @Column(name = "currency", nullable = false, length = 3)
    String currency
) {
    // Compact constructor for strict invariant validation
    public Money {
        Objects.requireNonNull(amount, "Amount cannot be null");
        Objects.requireNonNull(currency, "Currency cannot be null");
        if (amount.compareTo(BigDecimal.ZERO) < 0) {
            throw new IllegalArgumentException("Monetary amount cannot be negative");
        }
    }

    public Money add(Money other) {
        if (!this.currency.equals(other.currency())) {
            throw new IllegalArgumentException("Currency mismatch: " + this.currency + " vs " + other.currency());
        }
        return new Money(this.amount.add(other.amount()), this.currency);
    }
}

Why this matters:

  • Zero Setters: Once a Money object is instantiated, its state is frozen.
  • Fail-Fast Validation: The compact constructor catches bad data instantly, long before it ever touches a database transaction.

3. Enforcing State Machines with Sealed Interfaces

Business workflows rarely operate in a vacuum; they follow strict, regulated state transitions (critical in banking, payment processing, and digital onboarding). Instead of tracking states with fragile boolean flags, database strings, or loose enums, we can leverage OpenJDK JEP 409 (Sealed Classes and Interfaces) to model an algebraic data type (ADT) where the compiler strictly governs the closed set of allowed states: 

public sealed interface OrderState permits PendingState, PaidState, ShippedState, CancelledState {
    OrderStatus getStatus();
}

public record PendingState(LocalDateTime createdAt) implements OrderState {
    @Override public OrderStatus getStatus() { return OrderStatus.PENDING; }
}

public record PaidState(LocalDateTime paidAt, String transactionId) implements OrderState {
    @Override public OrderStatus getStatus() { return OrderStatus.PAID; }
}

public record ShippedState(LocalDateTime shippedAt, String trackingNumber) implements OrderState {
    @Override public OrderStatus getStatus() { return OrderStatus.SHIPPED; }
}

public record CancelledState(LocalDateTime cancelledAt, String reason) implements OrderState {
    @Override public OrderStatus getStatus() { return OrderStatus.CANCELLED; }
}

Exhaustive Pattern Matching for Transitions

Because OrderState is sealed, the Java compiler knows every possible implementation. Combined with Pattern Matching for switch (JEP 406 / JEP 441), we can implement state transition methods that guarantee compile-time exhaustiveness without brittle default: fallbacks: 

public Order pay(String transactionId) {
    this.state = switch (this.state) {
        case PendingState p -> new PaidState(LocalDateTime.now(), transactionId);
        case PaidState _, ShippedState _, CancelledState _ -> 
            throw new IllegalStateException("Cannot pay an order in state: " + this.state.getStatus());
    };
    return this;
}

If a new state is added to the system later, the compiler will instantly flag every switch statement that fails to account for it.

4. Persisting Sealed Hierarchies with Spring Data JPA

Bridging rich, immutable domain models with relational persistence has historically been an impedance mismatch. However, modern Spring Data JPA (3.x+) and Hibernate 6 handle record-based embeddables and polymorphic inheritance hierarchies cleanly. Using a single-table or joined-table strategy, we map domain states directly to database entities while preserving rich domain behavior: 

@Entity
@Table(name = "orders")
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "state_type", discriminatorType = DiscriminatorType.STRING)
public abstract class OrderEntity {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    // Entity mapping details...
}

@Entity
@DiscriminatorValue("PAID")
public class PaidOrderEntity extends OrderEntity {
    private LocalDateTime paidAt;
    private String transactionId;
}

5. Key References & Canonical Reading

  • Martin Fowler (2003): AnemicDomainModel — The canonical architectural definition and critique of entities stripped of business behavior.
  • Eric Evans (2003): Domain-Driven Design: Tackling Complexity in the Heart of Software (Addison-Wesley) — Foundational definitions of Value Objects, Entities, and Aggregate Invariants.
  • OpenJDK JEP 395: Records — Official specification for Java record classes as transparent, immutable data carriers.
  • OpenJDK JEP 409: Sealed Classes — Restricting which classes or interfaces may extend or implement them for exhaustive algebraic modeling.
  • Yaron Minsky (2011): Effective ML: "Making Illegal States Unrepresentable" — The type-driven design philosophy of encoding domain constraints directly into the compiler type system.
  • Spring Data JPA Reference: Spring Data JPA & Jakarta Persistence — Aggregate root boundaries, lifecycle management, and embeddable records support in Spring Boot 3.

Final Thoughts: The Shift Toward Compiler-Driven Architecture

Moving away from anemic domain models isn't just about syntax—it's a philosophical shift in how we handle safety. By leveraging Java 17 records for immutable values and sealed hierarchies for state machines, we delegate validation and architectural enforcement to the compiler.

When your IDE stops you from writing code that permits illegal business states, your production runtime becomes significantly more resilient.
